# 产品需求文档（PRD）

PRD 回答“做什么、为什么做、做到什么算成功”，面向用户价值，不写实现方案。实现方案、接口和数据由 [sdd.md](sdd.md) 的 spec 负责；PRD 获批后再写 spec。

## 何时写

- 新功能、较大的行为变更，或需求涉及多个角色 / 场景、范围不清时，写入或修订 PRD。
- 小改动、Bug 修复、名称确定的机械改动不写，直接按 [sdd.md](sdd.md) 或 issue 处理。
- 用户明确说“写 PRD”时必写。

## 写之前

- 先看项目上下文（相关代码、文档、已有 issue 和最近提交），能自己查到的事实不问。
- 一次只问一个问题，问目标用户、要解决的问题、成功标准和约束。用户要求深入追问时按 [grilling.md](grilling.md)。
- 不编造缺失信息：没有数据支撑的指标和结论标为待定。

## 路径与提交

- 每个项目只有一份 PRD：`docs/wukong-code-projects/prd.md`。新需求、需求变化都在这份文档里修订，不为每个功能另建 PRD 文件，也不带日期后缀。
- 文档不存在才新建；已存在先读完再改，只改与本次需求相关的章节，不重写无关内容。
- 头部写 `Status: Draft | Confirmed`、`Last updated`（修订日期）。末尾维护“修订记录”章节：日期、改了什么、为什么、关联 issue / PR 链接，最新的在前。
- 每次修订单独提交，提交信息写清改了哪部分需求。

## 章节结构

1. **背景与问题**：谁遇到什么问题，现状如何，为什么现在做；附已核实的事实和来源。
2. **目标与非目标**：要达成的结果；明确不做的事。
3. **用户与场景**：目标用户 / 角色，核心使用场景，写成“作为 <角色>，我想 <做什么>，以便 <得到什么>”的用户故事。
4. **功能需求**：按优先级（Must / Should / Could）列出，每条一句话说清行为，可编号（`FR-1`）供 spec、测试和 PR 引用。
5. **非功能要求**：性能、安全、兼容、可访问性、运维等，只写与本需求相关且可衡量的。
6. **验收标准**：对应每条 Must 需求，写成可检验的条目（给定 / 当 / 则，或明确的通过条件）；不用“体验良好”这类模糊说法。
7. **成功指标**：上线后如何判断有效；没有可测指标就写“待定”，不要硬凑。
8. **范围外与风险**：依赖、假设、风险和对策。
9. **待定事项**：未决问题、负责确认的人；标明是否阻塞 spec。
10. **修订记录**：见上文，每次修订追加一条。

## 自查

- 有没有占位符（TBD / TODO）、自相矛盾或有歧义的要求。
- 每条 Must 需求是否都有验收标准；是否混入实现细节（技术选型、表结构、接口）——有就移到 spec。
- 需求是否按功能分节、互相不混杂；已被取代或下线的需求标记为 `Deprecated` 并保留编号，不直接删除。

## 批准

请用户审阅 PRD 文件，明确同意后才写 spec；对聊天里的总结表示认可不等于批准文件。需求变化时先修订这份 PRD 并请用户确认修订部分，再改 spec 和代码。PR 描述链接 PRD，并按验收标准逐条说明是否满足。
