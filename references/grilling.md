# 逐题追问（grilling）

只在用户明确要求深入追问不清楚的功能、重构、架构选择或复杂实现时使用。名称确定的机械改动直接改；根因不明的故障按 [debugging.md](debugging.md) 处理。

- **确认前只读**：用户确认共识记录之前，只做只读调研和对话，不建或改文件、不跑测试、不实现、不改外部状态。
- **先调研再提问**：先查代码、测试、文档、Git 历史和必要的权威资料；能查到的事实不问。重要事实仍不确定或来源冲突时，说明查过什么，只在会影响实现时才问。
- **按依赖排序**：维护一张决策依赖图，记录每个决定的上游依赖、状态（未决 / 已确认 / 委托默认 / 已关闭 / 需复核）、依据的事实、关闭原因和受影响的下游。每次挑最上游的未决决定，不按固定问卷提问。
- **每轮只问一个决定**，消息依次包含：刚确认的结论或本题需要的最少证据；一个决策问题；已知答案范围时给出互斥选项；**推荐**的答案和简短理由；请用户明确作答。回答后复述新确认的结论，再进入下一题。
- 只问会改变范围、行为、风险、成本或验收结果的选择；影响小且可逆的细节给出推荐默认值，写进记录，不单独问。
- **冲突处理**：新回答与已确认的决定、已核实的事实或硬约束冲突时，先停下解决这一处冲突。上游决定变化时，只重开有具体因果依赖的下游决定，其余保持已确认并明确列出。
- **覆盖面**（相关时考虑，无关的直接关闭）：目标、用户价值、范围与非目标；现有系统的事实与约束；接口、组件边界与依赖；数据模型与数据流；兼容、迁移与回滚；错误、边界情况与安全影响；性能、可维护性与运维；测试、验收标准与交付。
- **完成条件**：所有影响实现的决定都已确认或明确委托；每个关闭的分支都有原因；没有未解决的事实冲突；剩余的未决事项都明确不阻塞。
- **共识记录**：满足完成条件后，在对话里给出完整记录，依次为：目标、已核实事实、已确认决定、已关闭分支、约束与非目标、授权默认值、不阻塞的未决事项、成功标准；附上推荐（确认，或修正某一节），请用户明确确认。
- **写 spec**：用户确认记录后，按 [sdd.md](sdd.md)「澄清需求与写 spec」的路径和章节结构另写一份技术 spec，头部写 `Status: Confirmed`、`Date`、`Source: grilling`。内容只来自已确认的结论：关闭的分支写成非目标或约束，授权默认值写成明确的默认，未决事项保留为待定；不要把共识记录或对话原样贴进去，也不加新范围。只提交这一个 spec 文件，然后请用户审阅；用户明确批准 spec 文件后才写实施计划。
- **中途停止**：用户说停就立即停止提问，按同样结构给出部分记录并标出阻塞项，不写也不提交 spec。
- 语气坚持、严谨、合作、尊重：质疑矛盾和没有依据的假设，而不是质疑人。
