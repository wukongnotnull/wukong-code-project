# 编码准则

改编自 [Karpathy Guidelines](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/skills/karpathy-guidelines/SKILL.md)（MIT），用来减少常见的 LLM 编码失误。这些准则偏向谨慎而不是速度，琐碎改动自行判断。已由其它细则覆盖的内容只给链接，与目标项目自身规则冲突处以项目为准。

## 先想清楚再写

- 动手前写明所做的假设；有更简单的做法就说出来，该反对时反对。
- 一处需求有多种理解时摆出来，不悄悄选一种。何时提问、怎么问按 [sdd.md](sdd.md)：能自己查到的事实不问，名称确定的机械改动直接改。

## 简单优先

- 只写解决问题所需的最少代码，不做没要求的功能。
- 不为只用一次的代码建抽象，不加没要求的“灵活性”或可配置项，不为不可能出现的情况写错误处理。
- 写完回看：200 行能写成 50 行就重写。自问资深工程师会不会觉得过度复杂，会就简化。

## 精准改动

- 只改必须改的。不顺手“改进”相邻的代码、注释或格式，不重构没坏的东西，沿用现有风格，即使自己会写得不一样。
- 自己的改动造成的无用 import、变量和函数要删掉；原本就存在的死代码不删，提一句，或按 [issues.md](issues.md) 建 issue。
- 检验标准：每一行改动都能直接追溯到用户的需求。

## 以可验证的目标驱动

- 把任务转成可验证的目标再做，例如“加校验”变成“为非法输入写测试，再让它通过”；测试先行的做法见 [tdd.md](tdd.md)，修 Bug 见 [debugging.md](debugging.md)。
- 不需要写实施计划的多步骤任务，先列简短计划，每一步写明怎么验证（`1. 步骤 → 验证：检查项`）；需要写计划的按 [sdd.md](sdd.md)。
- 成功标准明确才能独立循环到验证通过；“让它能用”这类模糊标准要先澄清。是否完成按 [verification.md](verification.md) 判断。
