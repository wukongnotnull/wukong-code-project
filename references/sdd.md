# 规范驱动开发（SDD）

需求较大或范围不清时，先按 [prd.md](prd.md) 写 PRD 并获批，再写 spec。

先有经用户批准的规范（spec），再按规范写计划和代码；规范是实现、测试和验收的唯一依据。

- 实现过程中需求或设计有变化，先更新 spec 并请用户确认，再改代码，不让代码和 spec 各说各话。
- PR 描述链接对应的 spec 和计划，按 spec 里的验收标准逐条说明是否满足。

## 澄清需求与写 spec

- 新功能、行为变更或意图不清的需求，先澄清再动手。名称确定的单处机械改动（改错字、指定文件的一行修复）直接改，不必写 spec。
- 先看项目上下文（相关代码、文档、最近提交），再提问：一次只问一个问题，问目的、约束和成功标准；能自己查到的事实不要问。
- 需求清楚但仍属行为变更时，用不超过 5 条要点说明方案，得到一次确认后实施；跨模块或多步骤的工作再写实施计划。
- 需求不清时，给出 2–3 个方案及取舍和推荐，分段确认设计，然后写 spec：
  - 路径 `docs/wukong-code-project/specs/YYYY-MM-DD-HHmm-<topic>-design.md`（24 小时制本地时间，`<topic>` 为英文 kebab-case），单独提交。
  - 内容依次为：问题与目标；架构与组件边界；接口、数据与行为；约束、兼容性与非目标；错误处理与运维；验收标准与测试。每条要求都要有已确认的决定或已核实的事实作依据，不写未确认的选项，未决事项标为待定。
  - 写完先自查：占位符（TBD/TODO）、自相矛盾、有歧义的要求、一份 spec 是否混了多个独立子系统。
  - 请用户审阅 spec 文件，明确同意后才写实施计划或代码；对聊天里的总结表示认可不等于批准 spec 文件。
- 用户明确要求“逐题问清楚”、深入追问或逐个决定时，改用 [grilling.md](grilling.md) 的流程，它产出的 spec 同样走上面的审阅步骤。

## 实施计划

- spec 获批且工作跨模块或多步骤时，写计划到 `docs/wukong-code-project/plans/YYYY-MM-DD-HHmm-<feature-name>.md`。
- 开头写目标（一句话）、架构（2–3 句）、技术栈，以及从 spec 原样摘出的全局约束。
- 先列出要新建或修改的文件及各自职责，再拆任务；每个任务有独立可测试的交付物，写明涉及的文件、依赖和产出的接口。
- 任务内的步骤按“写失败的测试 → 运行确认失败 → 最小实现 → 运行确认通过 → 提交”拆分，写出具体命令和预期结果。
- 历史 spec 与计划通过 Project README 索引查阅，见 [github-projects.md](github-projects.md)。
